# 哔哩哔哩勋章粉丝牌升级 — 代码审查 + 优化版

原脚本 v1.14（无夏不春风orz），优化版在此基础上做**针对性修复**，UI、配置项、接口行为均保持原样。

## 怎么用

1. 打开篡改猴 → 管理面板 → 找到「哔哩哔哩勋章粉丝牌升级」→ 删除（或先备份）
2. 新建脚本，把 `哔哩哔哩勋章粉丝牌升级-优化版.user.js` 全文粘进去 → Ctrl+S
3. 刷新直播间页面。原配置保存在 `localStorage` 的 `BILI<uid>_CONFIG`，键名完全一致，**不用重设**

## 改了什么

### 会导致功能静默失效的（原版就有）

| # | 问题 | 后果 |
|---|---|---|
| 1 | `BAPI.vip_point_task_combine()` **在 BilibiliAPI 里根本没定义** | 大会员签到成功后立刻抛 TypeError，积分永远查不出来。已补上实现 |
| 2 | `@connect bilibili.com` 不匹配子域 `api.bilibili.com` | 首次安装取 nav 会被篡改猴拦一次；拒绝授权就无限重试刷屏。已补 `api.*` / `live-trace.*` |
| 3 | `showinfo()` 里 `document.getElementById('user_info')` 为 null 时抛错 | B 站一旦改 `.player-ctnr` 那串内部类名，面板挂不上 → 抛错 → **后续自动任务完全不启动**。已加 fallback 到 body + 删除该函数 |
| 4 | 主循环无 try/catch | 任一接口异常就让递归链断掉，只能刷新页面。已包 catch，60 秒后自恢复 |
| 5 | **重复运行检测会把自己误杀** | B 站 SPA 路由切换会重新注入脚本，上一个实例刚写入的 `js_running_mark` 会把新实例判成「已在运行」→ `StartPlunder` 不执行 → **整个设置面板不出现，看起来像脚本坏了**。已用 `sessionStorage` 区分「本标签页重载」与「另一标签页真在跑」，检测窗口 20s→6s |

### 稳定性 / 正确性

- 配置加载原来靠 `JSON.parse(null)` 抛异常走 catch 兜底，且 `p.reject()` 无人接 → unhandled rejection。改为显式判空，永远 resolve，并对数组/数字型配置做脏数据修正
- `data.data.special_list.length` 无防御 → 接口少字段直接崩。已改 `Array.isArray`
- `roomHeart.start()` 返回 false（房间信息取不到）时，原版仍然白等 30 分钟。已改为跳过
- `sub_title.match(/\d+/)[0]`：B 站文案一改（无数字）就抛错。已加 `parseMinutes()` 安全取值
- 表情不足 10 个时 `dmlist[h]` 是 undefined，会把 `undefined` 当弹幕发。已加边界
- **wbi 签名密钥**：原版硬编码 `7cd0849…/4932caf…`。我核对过 B 站当前 nav 接口，这两个值**目前仍是线上默认值，没失效**——所以不是紧急 bug。但脚本明明已经从 nav 取到了 `img_key/sub_key` 却丢在 `Live_info` 里没用，将来轮换必挂。已改为动态注入，硬编码只留作兜底（签名结果与原来完全一致，向后兼容）
- wbi 参数改为按 key 字典序排序（原版是手工固定顺序，不合规）

### 性能

- `js_running_mark` 心跳从每 2 秒序列化整个 CONFIG 写 localStorage → 5 秒（检测窗口同步放宽到 20 秒）
- `GetEmoticons()` 原来在勋章循环内**每个勋章都请求一次**同一个接口，已提到循环外
- 昵称/会员名等插入 `innerHTML` 前统一转义（`esc()`），toast 改用 `textContent`

### 删掉的死代码（约 100 行）

- 粉丝节签到整块（`DoSignIn` / `ListSignInInfo` / 两个 API）：函数开头 `if (ts_s() > 1774976353) return`，2026-04-01 之后**永不执行**
- `String.prototype.replaceAll` 覆盖：原生早已支持，覆盖成 `new RegExp()` 后遇到正则特殊字符会出错
- `new_auto_heartbert` 与 `auto_heartbert` 互为重复实现，合并为一份（用较新的 dotime 计算逻辑）
- `Live_info` 中未被引用的 `rnd / user_level / identification / buvid3` 字段

### 保留没动的

- `hide_Toast` 这个键名语义是反的（`true` = 弹出提示），但改名会让老用户配置失效，所以只加注释
- 观看任务与点赞/弹幕任务仍是两条并行循环——B 站同一时刻只允许一个勋章涨亲密度，这是原设计，改了行为变化太大

## GitHub Actions 每日任务（2026-10-18 新增）

油猴脚本只能在浏览器里跑，关电脑就停。所以把**不需要长时间挂机**的部分搬到了 Actions。

### 做什么 / 不做什么

| 任务 | Actions | 说明 |
|---|---|---|
| 大会员权益领取（含漫画福利） | ✅ | |
| 大会员经验包 / 积分签到 | ✅ | |
| 粉丝牌点亮（点赞） | ✅ | 实测 `click_time=30` 一次即可从 `is_lighted:0` 变 `1` |
| 主站观看 + 分享 | ✅ | |
| **直播挂机（X25Kn 心跳）** | ❌ | 需要连续 30~60 分钟，是风控最敏感的部分，留在本地浏览器 |

### 配置（3 步）

1. 打开 `https://github.com/yu-echo/bilibili-medal-optimized/settings/secrets/actions`
2. 添加两个 Repository secrets：

| Name | Value |
|---|---|
| `SESSDATA` | 浏览器 F12 → Application → Cookies → `https://www.bilibili.com` → 找 `SESSDATA` 那一行的值 |
| `BILI_JCT` | 同上一栏里的 `bili_jct` |

3. 打开 Actions → 「B站每日任务」→ Run workflow（可勾 `dry_run` 先空跑一次）

### 定时

`cron: '0 1 * * *'` = 北京时间每天 09:00。**故意不卡零点**：Actions 的 cron 本来就不准时（高峰能延迟几十分钟），而点亮/权益这些任务对时间不敏感，亲密度重置交给本地脚本。

### 额度

单次运行约 2~3 分钟（点亮 30 枚 × 2 秒间隔）。私有仓库免费 2000 分钟/月，按 3 分钟/天算约 90 分钟/月，**额度完全够**。

### 无头环境的关键处理

Actions 里没有浏览器 cookie，拿不到 `LIVE_BUVID`。这里用了和 `XiaoYiWeio/asoul-support` 相同的办法：

```
GET https://api.bilibili.com/x/frontend/finger/spi   →   data.b_3  可直接当 buvid 用
```

### 已知限制

- **SESSDATA 会过期**（通常几个月），过期后 Actions 会报 `-101 账号未登录`，去 Secrets 里换新的即可
- **数据中心 IP 有风控风险**。先例项目因此把频率降到每周 1~2 次；这里保持每天 1 次，如果连续几天出现大量失败，把 cron 改成隔天更稳
- 点亮默认每次最多 30 枚（`MAX_LIGHT` 可调），避免一次请求过多触发风控

## 新增：大会员权益自动领取（2026-10-18）

原脚本只有「每日经验包」和「积分签到」，缺了 B币券/优惠券/漫画券这些实体权益。

| 接口 | 说明 |
|---|---|
| `GET /x/vip/privilege/my` | 查权益列表（带每项的 `recive_state`） |
| `POST /x/vip/privilege/receive` | 领取，参数 `type` + `platform=web` + `csrf` |

### 关键坑：`state` 字段和直觉相反

| 字段 | 实测含义 |
|---|---|
| `state = 0` | **有该权益，但还没领** |
| `state = 1` | 已领取 / 已激活 |
| `recive_state = 1` | 未领取 ← **唯一可靠判据** |
| `recive_state = 2` | 已领取 |

我最初按 `state===1 && recive_state===1` 过滤，结果一项都筛不出来——等于永远不会领。实测领了 type=5 之后 `state` 从 0 跳到 1，才反过来确认含义。

### 实测：10 项待领，只有 2 项真能领

| type | 结果 |
|---|---|
| 7（课堂优惠券） | ✅ `code 0` 领取成功 |
| 19 | ✅ `code 0` 领取成功 |
| 14 | `69818 已领取过，请到移动端会员中心查看` |
| 18 | `69825 淘宝账号查询异常`（需先绑定淘宝） |
| 20 | `6034019 饿了么领取活动已经过期` |
| 21 | `6034021 超大会员身份状态异常` |
| 24 / 25 / 26 / 27 | `-400 请求错误`（不支持网页端领取） |

**所以每轮只有 2 次有效请求，剩下 8 次全是白打。** 已加失败缓存：不可领的 type 写入 `BILI<uid>_VIP_SKIP`，**7 天内不再请求**（到期自动重试，万一是临时故障也能恢复）。实测第二轮 8 项全部被过滤，请求数降到 0。

## 当前直播间优先（2026-10-18 追加）

打开哪个直播间，那个直播间的粉丝牌就排到队首，观看和点赞/点亮都先处理它。

- 实现：`currentRoomId()` 优先读 `BilibiliLive.ROOMID`（真实房间号），拿不到再解析 URL
- `prioritizeCurrentRoom()` 把匹配的勋章 `unshift` 到第一位，其余顺序不变
- 两个循环（`auto_heartbert` / `like_msg`）都会调用，位置在排序和 `medal_first_uid` 置顶**之后**，所以优先级最高

实测：当前页 `33989` 在 89 枚勋章里位于第 18 位（index 17），改动后为第 1 位。

注意：短号直播间（如 `/6`）和真实房间号不同，如果 `BilibiliLive` 没加载出来会匹配不上——这种情况退化为原顺序，不会出错。

## B 站粉丝牌亲密度规则（官方公告核实，2026-10-18 查证）

### 旧规则（2025-09 之前）

| 等级 | 涨亲密度的方式 |
|---|---|
| 1–20 级 | 点赞首次 +100、弹幕首次 +100、观看每 5 分钟 +100（总和上限 1500）、银瓜子、电池、投币、充电 |
| **21–40 级** | **只能靠投喂电池/醒目留言/开通大航海 + 视频充电涨「航海亲密度」，看直播不涨** |

**「到一定等级不算亲密度」指的就是这条，分界线是 21 级。**

### 新规则（2025-09 改版，当前账号适用）

- 合并成 **1–120 级单一体系**，非大航海用户也能突破 20 级（21 级限制已取消）
- **观看直播**：每 5 分钟 +6 亲密度，**最多 30**
- **投喂粉丝团灯牌**：每日首个 +6
- **投喂电池 / 醒目留言**：1 电池 = 1 亲密度
- **视频投币**：1 硬币 = 10 亲密度，每日上限 100
- **视频充电**：1 B 币 = 10 亲密度
- 每日总上限：粉丝团 **2W** / 舰长 25W / 提督 100W / 总督 400W

### 对这套脚本的三个直接影响

1. **`day_limit=20000` 就是粉丝团的 2W 每日上限**，是真实值。我先前把它当成「接口占位值」判断错了
2. **新规则里没有「点赞」和「发送弹幕」给亲密度这一项**——它们只负责**点亮**。这正好解释了实测矛盾：点赞打到 `10/10`、`is_done=true`，但 `today_feed` 和 `intimacy` 一动不动
3. **等级不再是障碍**：29 级牌子照样有 `watchLive` 任务并会推进（15 分钟内 `0/10` → `4/10`）

**结论：这个脚本真正能涨亲密度的动作只有「观看直播」，点赞和弹幕的唯一作用是「把牌子点亮，从而解锁观看任务」。**

## 实测验证结果（2026-10-18，真实账号 89 枚粉丝牌）

用 Playwright 接上已登录的 Edge 实跑了一遍接口。**结论推翻了两个来自归档项目的假设**，这部分比之前的推测可靠。

### 1. 20 级并不封顶，`is_lighted` 才是关键

| 状态 | 实际下发的任务 |
|---|---|
| `is_lighted=1`（已点亮） | 5 个：`feedLight` / `watchLive` / `sendGift` / `sendDanmu` / `like` |
| `is_lighted=0`（未点亮） | 2 个：`sendDanmu` / `like`，副标题都是「仅点亮」 |

实测样本：28 级已点亮 → 有 watchLive；29 级未点亮 → 没有；19 级未点亮 → 没有；22 级已点亮 → 有。

**跟等级无关。**「20 级封顶」那个说法来自已归档的 fansMedalHelper，实测是错的，已回滚（没有改你的 `medal_pass_level`）。

推论很重要：未点亮的牌子得**先点亮**（发弹幕或点赞）才解锁观看任务。原脚本把「观看」和「点亮」两条循环**并行**跑，未点亮的牌子在点亮前查任务必然查不到 `watchLive`，那一轮就是白跳。所以新装脚本头几天看不到效果是正常的，等点亮任务先完成。

### 2. `day_limit` = 20000 的真实含义

`day_limit` 实测返回 **20000**（89 枚全是这个值）。我一开始以为是接口占位值，**这个判断是错的**——查官方公告后确认，新规则下粉丝团成员的每日亲密度上限就是 2W（20000），这个字段是真实值。

代码里取 `min(1500, day_limit)` 兜底仍然安全，但语义要从「占位值」改成「真实上限」。

### 3. 字段实测

- `medal` 对象 28 个字段，`today_feed` ✅ 存在（89/89）
- 佩戴字段是 **`wearing_status`**（1=佩戴中），**不是** `wear`（我先前猜错了，已修）
- `medal_id` ✅ 全都有 → 佩戴切换功能技术上可行
- `room_info` 只有 3 个字段：`room_id` / `living_status` / `url`

### 4. 你这批牌子的实际情况

| 项 | 数值 |
|---|---|
| 总数 | 89（无重复） |
| 点亮 / 未点亮 | **19 / 70** |
| 1–19 级 / 22–29 级 | 7 / 82 |
| 当日亲密度 | 88 枚为 0，1 枚为 7 |
| 当前在播主播 | 9 个 |

**所以原脚本对你最大的浪费不是「挂满的还挂」，而是「70 枚未点亮的牌子每枚都白挂 30 分钟」。** 加了 `hasWatchTask` 判断后这批会被直接跳过——实测数据支持这一条。

### 5. 点赞上限实测：确认是 10，但它不进 today_feed

对 33989（29 级牌子）连发 10 次点赞请求，每次 `click_time=30`，累计 300 次点击：

| | 操作前 | 操作后 |
|---|---|---|
| `like` 任务 | `每日上限 0/10` | **`每日上限 10/10`**，`is_done: true` |
| `today_feed` | 0 | **0（没变）** |
| `intimacy` | 1066 | **1066（没变）** |

四条结论：

1. **点赞上限确实是 10 点**：300 次点击 = 10 点，即每 30 次 1 点
2. **点赞得的亲密度不进 `today_feed`**——按 2025-09 新规则，点赞**根本不给亲密度**，只负责点亮（见上一节）。`today_feed` 为 0 是必然结果，不是延迟
3. **满了之后再点，接口照样返回 `code 0`，但一点都不涨**——原脚本没有 `is_done` 检查，每天会白打 300 次 × 89 枚
4. **上限随等级变化**：2 级牌子是 `2/2`，14 级是 `10/10`，不是全局 1500

已改：`like` / `sendDanmu` 四个分支全部加 `!task_info[t].is_done` 判断。

### 6. 心跳时序 + 挂满 15 分钟的实测

- E 握手成功后**必须等满 `heartbeat_interval`（60 秒）**才能发 X。抢跑返回 `1012002 time check failed`
- X 的 `s` 签名要求 payload 和 body 里的 `ts` **完全一致**。两次独立 `Date.now()` 差几毫秒就报 `1012001 sign check failed`（原脚本用 `const t = {...ts: this.ts...}` 只求值一次，是对的）

**连续挂机 15.7 分钟（15 次 X 全部成功、0 失败）的实测曲线：**

| 时间点 | X 成功次数 | `watchLive` 任务 | `today_feed` | `intimacy` |
|---|---|---|---|---|
| 起始 | 0 | `0/10` | 0 | 1066 |
| 5.2 分 | 5 | **`3/10`** | 0 | 1066 |
| 10.5 分 | 10 | **`4/10`** | 0 | 1066 |
| 15.7 分 | 15 | `4/10` | **0（没变）** | **1066（没变）** |

结论：

1. **心跳链路稳定**，15 次连续调用零失败，`RoomHeart` 的实现可以放心用
2. **任务进度确实在走**（`0/10` → `4/10`），说明心跳被服务端认可
3. **但 `today_feed` 和 `intimacy` 全程纹丝不动**。按新规则观看应得 6 亲密度 / 5 分钟，15 分钟约 18 点，但数值没变

第 3 点有两种可能，**目前无法区分**：
- ① `today_feed` 是结算后才刷新的（次日），当天查不到
- ② 该牌子存在别的限制

要确认只能等次日再查同一个牌子的 `today_feed` 有没有变成正数。原脚本所有「成功/失败」toast 只代表接口受理了，不代表亲密度到账——这一点是确定的。

另外 `watchLive` 从 `3/10` 涨到 `4/10` 后就不再动了，即使又多跑了 5 分钟——说明任务计数不是简单的「每 N 分钟 +1」，具体规则未摸清。

### 关于「佩戴粉丝牌」这一项（已实测，2026-10-18）

接口：`POST https://api.live.bilibili.com/fans_medal/v1/fans_medal/wear_medal`，body 只需 `medal_id` + `csrf`。

实测过程：原佩戴 9353811（14 级）→ 戴 2226（29 级）→ 恢复 9353811。三次调用全部返回 `code 0 "佩戴成功"`，最终状态已复原。

**必须知道的坑：`wearing_status` 有约 5 秒缓存延迟。**

- 戴完立刻查 panel，返回的还是旧牌（我第一次查就误判成「假成功」）
- 等 5 秒后 `wearing_status` 才翻转，`user/get_user_info` 的 `medal.level` 同步更新

这直接影响实现：`wearMedal` 之后如果立刻发弹幕，可能还是算在旧牌上，**必须等 5 秒以上**。

副作用确认：会真实改掉你直播间正在展示的粉丝牌。脚本里必须在发完后恢复原牌，且恢复失败要有兜底。
